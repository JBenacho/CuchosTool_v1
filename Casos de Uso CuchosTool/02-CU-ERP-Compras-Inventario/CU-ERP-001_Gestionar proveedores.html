1. INFORMACIÓN GENERAL
ID / Código: CU-ERP-001 [Trazabilidad: RF-CO-001, US-113, BR-02, BR-03] Nombre: Gestionar proveedores Objetivo: Administrar el ciclo de vida del maestro de proveedores (creación, actualización, homologación y consulta de estado comercial y tributario). Actor Principal: COMPRAS (ACT-09) (Autenticado / JWT interno) Actores Sec.: CONTADOR (ACT-07), Cloud SQL PostgreSQL, Cloud Logging Tipo / Prioridad: Administrativo / Maestro Prioridad Alta / Esencial Estado / Alcance: Aprobado / ERP Backoffice (Restringido a compras y finanzas bajo RBAC) Disparador: El analista de compras solicita registrar o actualizar los datos y condiciones de un proveedor. Precondiciones: 1. Usuario interno autenticado con rol COMPRAS o CONTADOR.
2. Documento fiscal (NIT/RUT) disponible para validación tributaria. Postcondiciones: Registro de proveedor persistido en esquema ERP con estado ACTIVO o SUSPENDIDO y log de auditoría. Resultado Exitoso: HTTP 201/200 con SupplierDTO estructurado y confirmación de persistencia.
2. DIAGRAMA DE CASOS DE USO (UML)
3. DESCRIPCIÓN Y ALCANCE

Controla el maestro de personas naturales y jurídicas que abastecen inventario de herramientas e insumos al ERP de CuchosTool.

Frontera E-Commerce vs ERP: Dominio exclusivamente interno. Los proveedores no interactúan con el E-Commerce público; sus datos residen en el esquema ERP sin exposición pública.

4. REGLAS DE NEGOCIO (RN)
  • RN-PRV-01 (Unicidad Fiscal): El NIT/RUT con dígito de verificación debe ser único en la tabla suppliers.
  • RN-PRV-02 (Régimen Tributario): Es obligatorio clasificar el régimen (Responsable de IVA / No Responsable / Gran Contribuyente).
  • RN-PRV-03 (Condiciones de Pago): Plazo de crédito predeterminado en días (0 para contado, 30, 60, 90 días).
  • RN-PRV-04 (Control de Estado): Proveedores con incidencias de calidad reiteradas pasan a SUSPENDIDO e impiden nuevas órdenes.
  • RN-PRV-05 (Default Deny): Acceso restringido a roles COMPRAS, CONTADOR y GERENTE_GENERAL.
5. FLUJO PRINCIPAL (CAMINO FELIZ)
  • 1 Solicitud de Gestión: El analista de compras envía petición POST /api/v1/erp/suppliers con los datos corporativos, fiscales y de contacto.
  • 2 Validación de Acceso: El API Gateway y middleware RBAC verifican el token JWT y el permiso purchases:write.
  • 3 Comprobación de Duplicidad: Supplier Service verifica en Cloud SQL que el NIT no exista previamente registrado.
  • 4 Validación Fiscal y Bancaria: Se valida la consistencia del dígito de verificación y la información de la cuenta de giro.
  • 5 Persistencia en Base de Datos: Se inserta el registro en la tabla erp_suppliers con estado inicial ACTIVE.
  • 6 Registro de Trazabilidad: Se emite log estructurado JSON a Cloud Logging con el usuario que ejecutó la acción y el NIT registrado.
  • 7 Confirmación: El servicio responde HTTP 201 Created con SupplierDTO consolidado y queda disponible para órdenes de compra.

8. FLUJOS ALTERNATIVOS / EXCEPCIONES
Código Situación Comportamiento del Sistema
FA-01 NIT duplicado en BD HTTP 409 Conflict. Rechazo inmediato indicando que el proveedor ya existe.
FA-02 Token ausente o rol no autorizado HTTP 401/403 Forbidden bajo la política Default Deny.
FA-03 Formato de NIT inválido HTTP 400 Bad Request detallando fallo en dígito de verificación o formato.
FA-04 Proveedor inactivo/suspendido HTTP 422 Unprocessable si se intenta asociar a nuevas órdenes de compra.
FA-05 Fallo en Cloud SQL HTTP 500. Notificación en Cloud Logging y mensaje amigable de reintento.
9. DATOS UTILIZADOS
  • Entidad Supplier: id (SUP-XXXX), taxId (NIT), dv, businessName, taxRegime.
  • Contacto & Ubicación: email, phone, city, address, contactPerson.
  • Condiciones Comerciales: paymentTermsDays (0, 30, 60), bankAccount, bankName.
  • Control de Estado: status (ACTIVE, SUSPENDED, INACTIVE).
  • Auditoría: createdBy, createdAt, updatedBy, updatedAt.
