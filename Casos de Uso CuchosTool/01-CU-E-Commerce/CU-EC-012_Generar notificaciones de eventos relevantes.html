1. INFORMACIÓN GENERAL
ID / Código: CU-EC-012 [Trazabilidad: RF-EC-006, RF-CORE-004, RI-EVT-001..005, US-012] Nombre: Generar notificaciones de eventos relevantes Objetivo: Consumir de forma asíncrona eventos de negocio desde Google Cloud Pub/Sub, formatear plantillas multicanal (Email/SMS) y garantizar su entrega trazable e idempotente. Actor Principal: Sistema / Notification Worker (Proceso asíncrono en Cloud Run) Actores Sec.: Google Cloud Pub/Sub, Gateway Email/SMS, Cloud SQL, Cloud Logging Tipo / Prioridad: Asíncrono / Event-Driven Prioridad Alta / Esencial Estado / Alcance: Aprobado / Plataforma Transaccional (Consumo desacoplado con DLQ) Disparador: Llegada de mensaje a tópicos Pub/Sub (order.created, OrderPaid, OrderDispatched). Precondiciones: 1. Mensaje publicado con schema válido y traceId.
2. Suscripción Pub/Sub activa con cola de mensajes muertos (DLQ). Postcondiciones: Notificación entregada al proveedor externo, log guardado en notification_logs y ACK enviado. Resultado Exitoso: Mensaje despachado y confirmado en Pub/Sub; idempotencia registrada sin duplicados.
2. DIAGRAMA DE CASOS DE USO (UML)
3. DESCRIPCIÓN Y ALCANCE

Consume eventos asíncronos para comunicar confirmaciones de compra, facturación y despacho al cliente final.

Aislamiento y Frontera ERP: Desacoplamiento total guiado por eventos. El worker opera en segundo plano; no realiza consultas síncronas ni transacciones cruzadas sobre el ERP central[cite: 1, 2].

4. REGLAS DE NEGOCIO (RN)
  • RN-NOT-01 (Idempotencia): Verificación de eventId en notification_logs. Si ya existe, emite ACK sin reenviar[cite: 2, 3].
  • RN-NOT-02 (Resiliencia DLQ): Máximo 5 reintentos exponenciales; ante fallos continuos, deriva a Dead Letter Queue[cite: 3].
  • RN-NOT-03 (Privacidad / Ley 1581): Enmascaramiento estricto de datos sensibles y tokenización de enlaces transaccionales.
  • RN-NOT-04 (SLO Asíncrono): Procesamiento y despacho en ≤ 2 segundos tras la publicación en Cloud Pub/Sub[cite: 3].
  • RN-NOT-05 (Trazabilidad): Propagación mandatoria del encabezado traceId / correlationId[cite: 3, 7].
5. FLUJO PRINCIPAL (CAMINO FELIZ)
  • 1 Recepción de Evento: El suscriptor en Cloud Run recibe un mensaje push/pull desde Cloud Pub/Sub con payload JSON firmado[cite: 1, 2].
  • 2 Control de Idempotencia: Notification Worker consulta en Cloud SQL si el eventId ya fue procesado exitosamente[cite: 2, 3].
  • 3 Resolución de Plantilla: Se carga la plantilla HTML/Texto asociada al evento (ORDER_CONFIRMED, PAYMENT_RECEIVED, etc.).
  • 4 Inyección de Contexto: Se fusionan los datos del cliente, número de pedido y totales en COP respetando políticas de privacidad.
  • 5 Despacho al Proveedor: Se invoca la API REST del proveedor de mensajería (SendGrid / Twilio) con timeout estricto de 3s.
  • 6 Persistencia de Estado: Se inserta el registro en notification_logs con timestamp, estado SENT y CorrelationId[cite: 2, 7].
  • 7 Confirmación (ACK): El worker retorna HTTP 200 / ACK a Google Cloud Pub/Sub para retirar el mensaje de la cola activa.

8. FLUJOS ALTERNATIVOS / EXCEPCIONES
Código Situación Comportamiento del Sistema
FA-01 Mensaje duplicado Detección por eventId; emite ACK inmediatamente sin reenviar al cliente[cite: 2, 3].
FA-02 Fallo en API Email/SMS NACK a Pub/Sub para reintento con retroceso exponencial (máx. 5 reintentos)[cite: 3].
FA-03 Agotamiento de reintentos El mensaje se mueve automáticamente a la Dead Letter Queue (DLQ) para análisis[cite: 3].
FA-04 Payload JSON corrupto Rechazo y enrutamiento a DLQ sin provocar caídas del worker; log crítico emitido[cite: 3].
FA-05 Destinatario inválido Registro como FAILED en notification_logs y emisión de ACK para descartar[cite: 2].
9. DATOS UTILIZADOS
  • Payload Evento: eventId, eventType, traceId, timestamp, data{}[cite: 2, 7].
  • Datos de Entrega: recipientEmail, recipientPhone, templateId, channel (EMAIL/SMS).
  • Entidad NotificationLog: id, eventId, channel, status (SENT/FAILED), errorReason.
  • Trazabilidad: correlationId transmitido entre microservicios[cite: 2, 7].
  • Credenciales: API Keys de SendGrid/Twilio gestionadas en Secret Manager[cite: 2, 3].
10. CRITERIOS DE ACEPTACIÓN (DOD)
  • ✓ Consumo desacoplado asíncrono desde Cloud Pub/Sub[cite: 1, 2].
  • ✓ Control estricto de idempotencia por eventId[cite: 2, 3].
  • ✓ Protección con Dead Letter Queue (DLQ) ante fallos reiterados[cite: 3].
  • ✓ Latencia de despacho de eventos ≤ 2 segundos tras publicación[cite: 3].
  • ✓ Desacoplamiento total: cero impacto sobre bases transaccionales ERP[cite: 1, 2].
  • ✓ Auditoría de envíos y propagación de traceId a Cloud Logging[cite: 2, 7].

Nota de Gobernanza y Frontera Transaccional (SRS v5.0): El subsistema de notificaciones opera bajo el patrón de arquitectura orientada a eventos (Event-Driven Architecture)[cite: 1, 2].
