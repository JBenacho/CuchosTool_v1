CU-SEC-006 - Aplicar política de acceso a módulo

Proyecto: CuchosTool.com | Baseline: SRS v5.0 / ARQ v6.0 / BL v5.0
Módulo: Seguridad / IAM / DOM-SEC | Fecha: 02/09/2026
Responsable: Nicola | Rol: Arquitecto & Dirección Técnica
1. Información General
ID / Código: CU-SEC-006
Trazabilidad: RS-001, RNF-005, BL-019, BR-02, BR-03, BR-11[cite: 2]
Nombre: Aplicar política de acceso a módulo[cite: 2]
Objetivo: Evaluar e imponer en el Gateway/BFF las directivas de control de acceso (RBAC + ABAC) para permitir o denegar el consumo de endpoints por módulo funcional bajo Default Deny[cite: 2].
Actor Principal: Sistema (API Gateway / Policy Enforcement Point)[cite: 2]
Actores Sec.: BFF Router, Identity Svc (PDP), Cloud SQL, Pub/Sub
Tipo / Prioridad: Administrativo / Seguridad Prioridad Alta / Esencial[cite: 2]
Estado / Alcance: Aprobado / Interceptor Perimetral (Baseline v6.0)
Disparador: Recepción de solicitud HTTP entrante hacia una ruta de cualquier módulo protegido (DOM-GE, DOM-CM, etc.)[cite: 2].
Precondiciones: 1. Solicitud entrante con Bearer JWT vigente.
2. Políticas de autorización del módulo cargadas en la matriz IAM de caché/BD.
Postcondiciones: Acceso autorizado (passthrough downstream) o bloqueado (HTTP 401/403 con AuditEvent)[cite: 2].
Resultado: Evaluación exitosa (enrutamiento al microservicio destino) o HTTP 403 Forbidden.
2. Diagrama de Casos de Uso (UML)
3. Descripción y Alcance

Propósito: Funcionar como Policy Enforcement Point (PEP) perimetral, evaluando las políticas de acceso a nivel de módulo funcional e impidiendo la propagación de peticiones no autorizadas[cite: 2].

Acceso: Ejecutado de forma automatizada por el API Gateway/BFF bajo la política restrictiva de Default Deny[cite: 2].

Frontera ERP: Filtro de seguridad transversal en capa de borde. No ejecuta lógica contable, comercial ni transaccional; evalúa estrictamente permisos y atributos de contexto[cite: 2].

4. Reglas de Negocio (RN)
  • BR-02 / RN-SEC-001: Arquitectura Default Deny: todo módulo está bloqueado salvo regla explícita que permita el rol/permiso del solicitante[cite: 2].
  • RN-SEC-006: Validación modular obligatoria: el Gateway rechaza con HTTP 403 peticiones de usuarios sin el scope o rol habilitado para dicho módulo funcional.
  • RN-SEC-007 / RF-SEC-008: Emisión obligatoria de AuditEvent ante intentos de acceso denegados con registro de IP, ruta, usuario y timestamp.
  • RN-OPS-012: Sobrecarga de latencia impuesta por evaluación perimetral ≤ TBD ms (p99 Cloud Run).
5. Flujo Principal (Camino Feliz)
1
Recepción de Petición: Cliente envía solicitud HTTP hacia un endpoint protegido de módulo con Bearer JWT[cite: 2].
2
Extracción de Contexto: API Gateway intercepta la petición, valida firma del token y extrae claims de rol y ZoneId[cite: 2].
3
Identificación de Módulo: El router determina el módulo de destino (DOM-GE, DOM-CM, etc.) y busca su política asociada.
4
Evaluación de Política: PDP (Identity Service / Policy Engine) evalúa reglas RBAC + ABAC bajo Default Deny.
5
Veredicto Favorable: La política confirma que el rol del usuario posee permisos suficientes para el módulo solicitado.
6
Inyección de Cabeceras: Gateway inyecta X-User-Id, X-User-Role, X-Zone-Id y X-Correlation-ID sanitizados.
7
Passthrough Downstream: La solicitud se enruta al microservicio de dominio destino para su ejecución exitosa[cite: 2].

9. Datos Utilizados y DTO
  • ModulePolicyContext: Contexto inmutable de evaluación con userId, role, moduleId y path.
  • targetModuleId: Identificador normalizado del módulo funcional (ej. DOM-GE, DOM-CM).
  • X-Correlation-ID: Identificador de trazabilidad distribuida propagado downstream[cite: 2].
  • decisionVerdict: Resultado booleano de la evaluación (PERMIT / DENY).
  • sanitizedHeaders: Claims inyectados de forma segura hacia microservicios backend.
  • AuditDenialPayload: Estructura forense emitida ante rechazos por 403 Forbidden.
10. Criterios de Aceptación (DoD)
  • ✓ Evaluación obligatoria de Default Deny en cada endpoint de módulo (BL-019)[cite: 2].
  • ✓ Rechazo con HTTP 403 verificado ante ausencia del rol requerido para el módulo.
  • ✓ Sobrecarga de latencia del interceptor validada bajo SLA p99 / TBD documentado.
  • ✓ Pruebas negativas de inyección de cabeceras no autorizadas aprobadas (FA-01..05)[cite: 2].
  • ✓ Emisión de evento de auditoría ante cualquier intento de acceso bloqueado.
